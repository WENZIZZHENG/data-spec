## Context

DataSpec 的标准字段已经包含 `displayName`、`comment`、`aliases`、`category`、`tags`、`codeSetId`、`sensitive`、`status` 和 `exampleValue` 等 AI 语义字段。当前字段库能维护这些属性，但用户无法快速知道哪些字段质量低、哪些字段会让 AI 建表时缺上下文。

P6-5 第一版应优先做确定性、可测试、只读的质量报告，帮助用户定位低质量字段并跳转编辑。它不引入外部 LLM，不新增质量评分存储表，也不改变字段 CRUD 语义。

## Goals / Non-Goals

**Goals:**

- 按项目生成字段质量 summary 和字段明细。
- 对每个字段输出 `score`、`level`、`issues`、`suggestions` 和关键字段摘要。
- 覆盖高价值规则：缺注释、缺别名、缺示例值、缺分类/标签、疑似敏感未标记、枚举/状态字段未关联代码集、废弃/禁用字段缺替代说明。
- 前端提供质量视图，支持筛选低质量字段并跳转字段库编辑。
- 质量结果可被 AI/CLI/MCP 后续复用，结构保持机器可读。

**Non-Goals:**

- 不自动修改字段标准。
- 不保存历史评分，不做趋势 KPI。
- 不引入外部 LLM、向量检索或复杂语义模型。
- 不做批量修复入口；批量维护留给 P6-15。
- 不做字段重复/冲突检测；该能力留给 P6-8。

## Decisions

1. **实时计算，不新增数据库表。**
   - 理由：第一版只需要当前字段库的健康状态，评分由现有字段属性可确定计算；新增表会带来迁移、刷新和一致性成本。
   - 替代方案：保存每次扫描结果。暂不采用，后续若要趋势分析可在 AI 使用反馈或活动时间线中扩展。

2. **分数从 100 扣减，问题带 severity 和建议。**
   - 理由：用户容易按分数排序，AI 则需要结构化 issue 判断下一步动作。`ERROR/WARNING/SUGGESTION` 可复用 lint 语义。
   - 规则示例：缺注释扣 20，缺别名扣 10，缺示例扣 10，疑似敏感未标记扣 20，枚举/状态字段缺代码集扣 15，废弃/禁用字段缺替代说明扣 10。

3. **敏感/枚举判断使用轻量启发式。**
   - 理由：字段模型已有 `sensitive` 和 `codeSetId`，但历史字段可能未补齐；第一版用字段名、显示名、注释、标签中的关键字判断提示即可。
   - 替代方案：调用字段推荐或外部 LLM 判断语义。暂不采用，避免不稳定和依赖外部服务。

4. **前端新增独立质量页，而不是塞进字段库列表。**
   - 理由：质量报告有 summary、筛选、排序和 issue 展示，独立页面更容易扫描；跳转字段库编辑保持现有 CRUD 入口不变。

## Risks / Trade-offs

- [启发式误判] → 规则输出为建议，不自动修改；文案说明“疑似”并提供跳转编辑。
- [分数过于主观] → 第一版固定扣分并用单测锁定，后续再把阈值配置化。
- [字段量大时实时计算耗时] → 第一版复用 `listByProject`，P6-16 再处理大字段库性能基线。
- [前端和后端类型漂移] → 新增类型先手写并通过 `pnpm build` 校验；如后端 OpenAPI 可用，再更新 `schema.ts`。
