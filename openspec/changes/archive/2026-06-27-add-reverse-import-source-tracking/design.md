## Context

当前数据库直连反向导入只在确认导入时创建标准字段，导入结果只返回新增/跳过数量和字段名。字段进入标准库后，系统没有保存来源数据库、schema、table、column 或原始 metadata，后续无法判断字段是否来自数据库直连、来自哪次导入，也无法支撑 P6 覆盖率和未纳管字段盘点。

本次变更仍面向个人/小团队自用，不引入连接保存、同步任务、审批流或组织级治理。

## Goals / Non-Goals

**Goals:**

- 为数据库直连确认导入新增批次记录，保存来源摘要和导入统计。
- 为通过反向导入创建的标准字段新增来源记录，保存 schema/table/column、原始类型、默认值、可空、注释和 metadata 快照。
- 字段列表或详情可展示来源摘要，便于用户追溯字段来源。
- 保持普通手工字段、Excel 导入和现有字段 CRUD 不受影响。

**Non-Goals:**

- 不保存数据库密码或完整 JDBC 连接串。
- 不做定时同步、后台扫描或自动更新字段标准。
- 不自动删除、废弃或合并字段。
- 不做复杂血缘图谱、跨项目来源聚合或审批流。

## Decisions

1. **新增两张表而不是扩展 `ds_field`**
   - 批次表记录一次导入上下文，字段来源表记录字段级来源。
   - 理由：字段主表应保持标准字段本体语义，来源属于可选追踪信息；普通字段没有来源记录也应正常工作。
   - 替代方案：在 `ds_field` 加 source 字段；会让字段表继续膨胀，也难以表达一次导入包含多个字段和统计。

2. **确认导入时写入批次和来源**
   - `DatabaseImportReq` 现有 `candidates` 已包含 table/column/type/default/null/comment，第一版可复用这些数据写来源。
   - 批次中的 database/schema/tableNames 从数据库直连请求传入，字段来源中的 metadata 快照保存候选字段 JSON。
   - 替代方案：preview 阶段先创建批次；用户可能只预览不导入，会产生大量无效批次。

3. **不保存敏感连接信息**
   - 批次仅保存 `databaseType`、`databaseName`、`schemaName`、`tableNamesJson` 等非密码信息。
   - `host` 是否保存取决于实现时风险评估；第一版可不保存 host，或仅保存脱敏 host，用于本地复盘。
   - 密码和完整 URL MUST NOT 持久化。

4. **字段来源查询以字段 ID 为主**
   - 字段库列表可按需返回最近来源摘要，字段详情可查询完整来源列表。
   - 第一版优先提供字段来源查询 API 和最小前端展示，不要求所有字段列表分页接口一次性聚合复杂来源。

## Risks / Trade-offs

- **导入来源与字段创建事务不一致** → 导入候选、批次和来源写入应放在同一服务事务中；来源写入失败时本次导入整体回滚或明确失败。
- **重复导入同一字段只会跳过字段** → 跳过字段不新增来源记录，避免把未实际创建的字段误记为本次导入产物。
- **metadata 快照结构后续演进** → 使用 JSON 文本保存第一版候选快照，后续可以兼容新增字段，不需要频繁迁移列。
- **列表来源聚合增加查询成本** → 第一版可在字段详情或按字段 ID 查询来源，列表仅展示最近来源摘要或延后优化。

## Migration Plan

- Flyway 新增 `ds_reverse_import_batch` 和 `ds_field_source` 两张表及必要索引。
- 老数据默认没有来源记录，字段功能保持兼容。
- 回滚时可删除新增表；不影响 `ds_field` 现有数据。

## Open Questions

无。第一版按直连确认导入路径落地，SQL 粘贴反向导入来源可后续复用同一模型扩展。
