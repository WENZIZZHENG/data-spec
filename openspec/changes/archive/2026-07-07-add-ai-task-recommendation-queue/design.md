## Context

DataSpec 的能力已经从单点工具扩展到一组诊断和治理信号：字段质量、冲突、覆盖率、候选 Inbox、标准健康趋势、AI 反馈、质量门禁、使用热区等。问题是这些信号分散在不同页面和 API 中，AI agent 或用户需要自行判断“下一步最该做什么”。本变更是 SDD standard：新增只读 API 可观察契约，但不改变数据库 schema、写入语义、权限边界或前端导航。

## Goals / Non-Goals

**Goals:**

- 为项目生成 3 到 8 个推荐任务卡，帮助 AI 和用户选择下一步。
- 每张任务卡包含任务类型、优先级、原因、目标入口、可复制命令、证据引用和完成判定。
- 聚合已有安全摘要信号，优先覆盖低质量字段、热区治理、待处理候选、质量门禁和健康动作。
- 响应只包含摘要、计数、页面路由和命令模板，不返回 raw SQL、AI payload、候选 raw evidence 或凭据。

**Non-Goals:**

- 不新增表、迁移、后台调度、缓存或任务执行状态。
- 不自动执行任务，不自动采纳候选，不自动修改字段标准。
- 不新增前端页面、CLI 命令或 MCP tool；第一版只提供后端 API。
- 不替代 OpenSpec、AI workflow recipes 或人工判断，只提供推荐入口和完成判定。

## Decisions

1. 新增独立 `aitaskrecommendation` 模块。
   - 理由：推荐队列横跨多个诊断来源，独立 service 能保持编排逻辑清晰，不污染 dashboard、health 或 heatmap。
   - 备选：扩展 dashboard。放弃原因是 dashboard 面向首页指标，推荐队列是 AI 可消费的任务卡契约。

2. 第一版使用确定性规则生成任务卡。
   - 规则来源：标准健康 top actions、标准使用热区 high-risk items、待处理候选数量、质量门禁失败项或字段质量摘要。
   - 理由：无需引入 LLM 或调度器，输出可解释、可测试且可稳定回归。
   - 风险控制：每个任务卡都必须有 evidence refs 和 completion check，避免只给抽象建议。

3. 推荐任务不持久化。
   - 理由：第一版基于当前项目状态实时生成；任务是否“消失”由源信号变化决定。
   - 备选：新增任务表。放弃原因是会引入状态一致性和写入语义，不符合本轮最小闭环。

4. 命令和路由只指向已有能力。
   - 理由：AI 能复制命令或跳转页面执行已有安全路径；未实现的 future action 不进入第一版队列。
   - 风险控制：推荐命令使用项目 ID 参数模板，不包含 token、password、JDBC URL 或本地路径。

## Risks / Trade-offs

- 推荐顺序不一定符合所有项目偏好 → 第一版按 severity/priority/证据计数确定性排序，后续可加用户策略。
- 来源 API 可能为空或不可用 → 缺少某类信号时跳过对应任务，不阻断其他推荐。
- 实时聚合可能重复调用多个服务 → 第一版限制任务数量并复用摘要接口；后续再考虑缓存。
- 任务卡可能让 AI 误以为可以自动写入 → 响应只给入口、命令和完成判定，不包含自动执行标记。

## Migration Plan

- 部署：新增只读 API，无数据库迁移；旧客户端不受影响。
- 回滚：删除新增模块和 OpenSpec change 即可，不影响已有数据。
- 验证：新增 service/controller 单测，运行受影响后端测试、OpenSpec strict、`git diff --check`、敏感词扫描和独立子 agent 评审。
