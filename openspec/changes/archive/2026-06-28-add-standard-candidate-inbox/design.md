## Context

DataSpec 已有字段覆盖率、反向导入、字段推荐、字段质量和 AI 反馈报告，这些能力会产生“未纳管字段”“疑似标准字段”“需要补别名或修质量”的信号。但这些信号目前停留在各自页面，缺少一个持久化的候选池和决策记录。

P6-28 第一版面向个人/小团队：候选可以由 API 手动创建，也可以后续由覆盖率、反向导入或 AI 反馈逐步写入。当前实现优先保证候选状态机、人工采纳入口和 AI 可读决策结果稳定。

## Goals / Non-Goals

**Goals:**

- 新增项目级标准候选 Inbox，候选记录包含字段名、显示名、类型、注释、来源、证据、置信度、状态和关联字段。
- 提供候选列表、新建候选、接受为新字段、合并到已有字段、忽略、延后 API。
- 前端新增“标准候选”页面，支持筛选、查看证据和执行决策。
- 决策结果可被 AI 读取，避免重复推荐已忽略或已合并候选。
- 保持第一版可回滚、可测试，不引入审批流或后台队列。

**Non-Goals:**

- 不自动从所有现有页面批量生成候选；自动接入各来源留给后续增强。
- 不做企业审批、多人分派、权限矩阵或工单流。
- 不自动合并字段语义，不删除旧字段，不自动修改源数据库。
- 不读取业务数据行，不保存数据库密码、token 或完整连接串。

## Decisions

### 1. 使用独立候选表记录状态和决策

新增 `ds_standard_candidate`，字段包含 `project_id`、`candidate_name`、`display_name`、`data_type`、`comment`、`source_type`、`source_ref`、`evidence_json`、`confidence`、`status`、`target_field_id`、`decision_reason`、`decided_at`、`created_at`、`updated_at`。

备选方案是只在字段来源或质量报告中即时计算候选。它无需迁移，但无法记录忽略/延后/合并决策，AI 也无法知道哪些建议已经被用户处理。

### 2. 第一版用明确状态机而不是审批流程

状态使用 `PENDING`、`ACCEPTED`、`MERGED`、`IGNORED`、`POSTPONED`。所有写操作都需要当前项目访问校验；接受/合并/忽略/延后只更新候选和必要字段，不引入审核人、发布版本或团队流程。

### 3. 接受候选创建标准字段，合并候选只记录目标字段

接受候选时创建一个标准字段，优先使用候选的 name/type/comment/displayName/source 元数据；合并候选时记录 `targetFieldId` 和原因，不自动改目标字段别名或注释，避免误写正式标准。后续可以在候选详情中增加“建议补别名”的显式动作。

### 4. API 采用显式 action endpoint

候选列表和创建走 `/api/standard-candidates`，决策走 `/api/standard-candidates/{id}/accept|merge|ignore|postpone`。这样前端和 AI 能清楚区分读取、创建和高风险写入，后续接入 preflight 或 dry-run 时也更自然。

## Risks / Trade-offs

- [Risk] 第一版不自动从覆盖率/反向导入生成候选，页面初始可能为空。→ 提供创建候选 API 和前端手动新建入口，后续来源接入可以复用同一表。
- [Risk] 接受候选可能创建重复字段。→ service 在接受前按项目和字段名检查重复，重复时提示改用合并。
- [Risk] 合并不自动补别名会显得保守。→ 第一版优先避免误写，决策原因保留在候选中，后续可加显式“应用为别名”动作。
- [Risk] evidenceJson 结构可能随来源变化。→ 第一版作为 JSON 字符串保存，同时在前端以可复制文本展示；稳定字段仍放在候选顶层。

## Migration Plan

- 新增 Flyway 迁移创建 `ds_standard_candidate` 表和项目/状态/来源索引。
- 后端新增模块和 API，不改变已有字段、反向导入、覆盖率和 AI 反馈接口。
- 回滚时删除新增 API/页面和候选表；已创建的正式字段不自动回滚，仍可通过现有字段变更/回退能力处理。

## Open Questions
