## Context

字段服务已经支持单条 CRUD、批量归组和标准变更日志。`ds_standard_change_log` 保存 `beforeJson` / `afterJson`，但目前只能分页查看，不能按日志执行受控回退。字段库前端已经支持多选、分组筛选、来源和影响弹窗，可在同一页面承接批量维护和最近变更回退。

本次是 standard SDD：新增用户可见 API、前端流程和回退写入逻辑；不新增数据库表，不改变字段基础模型。

## Goals / Non-Goals

**Goals:**

- 对选中字段批量维护常用属性：`status`、`category`、`tags`、`sensitive`、`codeSetId`、`aliases`。
- 提交前提供只读预览，说明将影响哪些字段、哪些属性会变化、哪些字段没有变化。
- 批量维护必须保持项目边界：请求中的所有字段必须属于同一项目，否则拒绝且不部分写入。
- 基于现有字段变更日志执行单条回退，从日志 `beforeJson` 恢复字段关键属性，并写入新的回退日志。
- 前端字段库提供批量维护入口、预览确认和字段最近变更回退入口。

**Non-Goals:**

- 不做复杂批量撤销、审批流、草稿发布或多人协作锁。
- 不跨项目批量修改字段，不自动解决字段名冲突。
- 不回退 delete/create 记录，不恢复已逻辑删除字段。
- 不新增独立 undo 表；第一版复用现有变更日志作为证据链。

## Decisions

1. **批量维护复用显式 patch 语义。**
   - 方案：请求包含 `projectId`、`fieldIds`、`updates`；只有出现在 `updates` 中的 key 生效，空字符串或 null 表示清空可空属性。
   - 理由：用户可能只想改状态，不应覆盖分类、标签或别名。
   - 替代方案：提交完整字段对象。该方案容易误覆盖字段基础属性，且前端需要填充大量无关字段。

2. **preview 和 submit 使用同一套后端 diff 计算。**
   - 方案：新增 `previewBulkUpdate` 返回字段级变更项；`batchUpdate` 先复用 preview 的校验与 diff，再写入有变化的字段。
   - 理由：预览和提交一致，避免“预览说会变，提交变成另一套逻辑”。
   - 替代方案：前端自行 diff。该方案无法保证项目边界、状态合法性和后端规范化后的 tags/aliases 一致。

3. **回退使用日志 `beforeJson` 恢复字段关键属性。**
   - 方案：新增 `undoFieldChange(fieldId, logId)`；只允许 targetType=field、targetId=fieldId、action=update/undo 且 beforeJson 非空的日志；恢复字段可编辑属性后记录 `action=undo`。
   - 理由：现有日志已经是审计证据，新增表过重；新日志能保留“谁在什么时候回退了什么”。
   - 替代方案：覆盖原日志或只在前端填表。前者破坏审计链，后者无法形成可追溯回退记录。

4. **字段名回退仍走唯一性校验。**
   - 方案：如果 beforeJson 中的 name 与项目内其他字段冲突，拒绝回退并提示用户手动处理。
   - 理由：回退不能破坏字段库的不变量。

## Risks / Trade-offs

- [Risk] 批量维护误改大量字段。→ 提供 preview、确认弹窗和每字段变更日志；未选择任何更新 key 时拒绝。
- [Risk] 回退旧快照导致字段名冲突。→ 回退前检查项目内名称唯一性，冲突时拒绝。
- [Risk] JSON 快照格式未来变化。→ 第一版只恢复字段实体当前仍存在的关键属性，未知字段忽略；失败时返回业务错误。
- [Risk] 批量维护和 P6-14 批量归组能力重叠。→ P6-14 保留“分组快改”，P6-15 提供更完整的维护对话框和预览。

## Migration Plan

无需数据库迁移。新增 API 和前端入口可回滚；现有字段 CRUD、批量归组和变更日志分页不受影响。
