## Context

规则配置页当前通过 `RuleConfig.paramsJson` 维护规则参数。后端规则已经约定了常见参数键：`requiredColumns`、`forbiddenNames`、`recommendations`、`suffixTypes`、`prefixTypes`。用户长期维护时，如果直接手写 JSON，容易出现键名拼错、数组/对象结构错误和无法快速扫描的问题。

## Goals / Non-Goals

**Goals:**

- 为常见规则提供清晰表单：列表编辑、键值映射、后缀/前缀类型映射。
- 保存仍生成现有 `paramsJson`，兼容后端和已有数据。
- 列表中展示可读参数摘要，方便确认规则内容。
- 为转换逻辑补纯函数测试，并接入 `pnpm test`。

**Non-Goals:**

- 不新增后端接口、数据库表或迁移。
- 不实现复杂规则 DSL 或图形化规则编排器。
- 不改变 lint 规则语义和默认参数。
- 不处理多角色权限、审批和发布流程。

## Decisions

1. **前端结构化表单 + JSON 预览兜底**
   - 理由：常见规则可以通过稳定参数结构表达；保留 JSON 兜底能兼容未知规则和临时调试。
   - 替代方案：后端返回规则 schema；更规范但需要新增 API 和后端元数据，超出本轮边界。

2. **抽出纯工具函数**
   - 理由：JSON 与表单之间转换最容易引入隐性错误，独立测试比只靠页面构建更可靠。
   - 替代方案：全部写在 Vue 组件里；短期快，但难测试且后续扩展成本高。

3. **按 ruleCode 自动切换编辑器**
   - 理由：已有可用规则列表，ruleCode 是后端契约；前端无需新枚举接口。
   - 替代方案：用户手动选择参数类型；容易配置错。

4. **界面保持工作台风格**
   - 理由：规则配置是维护工具，应优先扫描、编辑和确认，不做装饰性页面。

## Risks / Trade-offs

- **旧数据可能包含未知 JSON 结构** → 结构化编辑器只处理已知键，仍保留 JSON 文本作为兜底。
- **用户输入逗号分隔类型可能有空值** → 工具函数统一 trim/filter，保存前输出干净数组。
- **规则参数摘要可能不完整** → 摘要只展示常见键，未知参数以 JSON 预览保底。
- **表单复杂度增加** → 将参数编辑分成规则专项区域，并保持原有基本字段不变。
