## Context

DataSpec 已经具备字段变更日志、标准快照、数据库反向导入批次、SQL 检查记录、DDL/AI 任务记录、API token 最近使用时间等数据源。当前问题不是缺少原始记录，而是这些信息分散在多个页面，个人或小团队排查“标准什么时候变了”“最近哪个 AI/CLI 操作过项目”时需要来回翻找。

本变更面向个人/小团队优先使用场景，目标是做一个轻量、只读、按项目聚合的活动时间线。它不是企业级审计中心，不承担权限审批、留存合规或不可抵赖审计。

## Goals / Non-Goals

**Goals:**

- 提供项目维度活动 API，聚合已有记录并按发生时间倒序返回。
- 为每条活动提供统一字段：动作类型、标题、描述、时间、操作者、来源、严重级别、详情跳转和少量安全 metadata。
- 在 Dashboard 展示最近活动，支持按动作类型筛选并跳转到相关功能页。
- 在不新增存储表的前提下，复用现有记录，避免扩大迁移和数据治理成本。

**Non-Goals:**

- 不实现审批流、发布流、权限模型、审计留存策略或不可篡改日志。
- 不记录 SQL 原文、token 明文、连接密码等敏感内容。
- 不为每个业务页面新增独立历史视图，只在工作台聚合关键活动。
- 不补齐历史上从未持久化的动作；仅展示已有可追溯记录。

## Decisions

1. **使用只读聚合服务，而不是新增 activity 表。**

   原因：现有记录已经覆盖主要来源，新增表会引入写入埋点、幂等和迁移成本。当前第一版只需要“最近发生了什么”，聚合读足够。

   备选方案：在所有业务动作写统一事件表。该方案更完整，但会放大本轮范围，也更接近企业级审计系统，暂不采用。

2. **时间线返回统一 DTO，metadata 只放安全摘要。**

   原因：前端需要稳定渲染和筛选，AI/CLI 也需要机器可读字段；metadata 仅保存数量、ID、状态等摘要，避免泄露 token、SQL 原文或数据库连接信息。

   备选方案：直接返回各表实体。该方案类型不稳定且容易泄露内部字段，暂不采用。

3. **按数据源各取有限数量后内存排序。**

   原因：数据源来自多个仓储和服务，当前规模是个人/小团队项目，内存合并可读性高且无需复杂 SQL union。服务层会限制 limit 上限。

   备选方案：数据库视图或 union 查询。该方案对多表结构耦合更强，也不便复用已有 service 边界，暂不采用。

4. **前端接入 Dashboard，而不是新增一级导航。**

   原因：活动时间线是工作台可观测能力，最适合作为项目概览的一部分；新增页面会增加导航负担。

   备选方案：独立“审计”页面。该方案表达偏重，不符合个人/小团队轻量定位，暂不采用。

## Risks / Trade-offs

- [Risk] 聚合服务只能展示已持久化的数据源，未落库动作不会出现。→ Mitigation：文档和规格明确第一版边界，后续需要时再为特定动作补充轻量记录。
- [Risk] 多源聚合字段含义不一致，前端文案可能不稳定。→ Mitigation：在服务层集中做标题、来源、严重级别和跳转规则映射。
- [Risk] token/SQL/连接信息误放入活动 metadata。→ Mitigation：metadata 只允许安全摘要，测试覆盖不返回敏感字段。
- [Risk] 多仓储查询影响 Dashboard 响应。→ Mitigation：每类记录限制数量，统一 limit 上限，个人/小团队规模下保持简单。

## Migration Plan

无需数据库迁移。发布后后端新增只读 API，前端 Dashboard 在有项目时加载活动；无记录时展示空态。

Rollback 时移除前端调用和后端活动包即可，不影响原有业务数据。
