## Context

DataSpec 已有标准字段、表模板、DDL 生成、SQL 检查记录、AI Context、标准快照、反向导入来源和字段变更日志。字段库当前可以编辑字段属性，但保存前无法看到该字段是否已经被模板引用、是否有反向导入来源、是否出现在历史 SQL 检查记录或标准快照中。P6-6 第一版要做“足够实用的轻量影响分析”，服务个人/小团队快速判断风险。

## Goals / Non-Goals

**Goals:**

- 为单个字段提供项目内只读影响报告。
- 汇总字段引用的模板、导入来源、SQL 检查记录、标准快照/AI Context 相关记录和自身关键约束。
- 在字段库详情/编辑入口显示影响摘要，并在保存关键字段前给出非阻断提示。
- 输出结构可被前端、CLI/MCP 或后续 AI 工作流复用。

**Non-Goals:**

- 不扫描生产查询日志或业务代码仓库。
- 不实现复杂字段血缘图、上下游作业图或跨系统 lineage。
- 不阻断字段保存，不引入审批、发布或权限流程。
- 不新增历史影响快照表；趋势留给 P6-53。

## Decisions

1. **实时只读聚合，不新增表。**
   - 理由：第一版影响范围主要来自现有表和记录，实时查询能避免缓存失效和迁移成本。
   - 替代方案：保存每次影响分析结果。暂不采用，后续需要趋势或证据包时再落库。

2. **用 `projectId + fieldId` 双参数限定影响查询。**
   - 理由：后端可先按 id 取字段，再校验字段归属项目，避免只按 fieldId 查询造成跨项目误读。
   - 替代方案：只传 fieldId。暂不采用，因为前端全局项目选择是核心上下文。

3. **影响项采用统一结构而非为每类来源做完全不同 DTO。**
   - 理由：前端和 AI 更容易消费 `impactType/sourceId/sourceName/count/severity/description` 这类稳定字段；详情字段放入 `metadata`。
   - 替代方案：为模板、记录、来源、快照分别返回复杂对象。暂不采用，避免第一版过度建模。

4. **编辑提示只提醒，不阻断。**
   - 理由：项目定位是个人/小团队工具，字段维护要轻快；影响提示帮助用户做判断，但不能变成企业发布流程。
   - 替代方案：保存前强制确认或禁止保存。暂不采用，审批/发布留给未来团队治理能力。

5. **SQL 检查记录采用轻量文本命中和记录数量。**
   - 理由：历史记录里 SQL 原文和 issue JSON 可用于判断字段是否出现；第一版用字段名/显示名的保守匹配即可提示可能影响。
   - 替代方案：重放所有历史 SQL AST 并建立索引。暂不采用，成本高且容易变成血缘系统。

## Risks / Trade-offs

- [历史 SQL 文本命中可能误报] → 标记为 `POSSIBLE_REFERENCE`，只作为提示，不阻断编辑。
- [实时查询在大项目中变慢] → 第一版限制取最近记录和摘要数量；P6-16 再做性能基线。
- [影响类型不够全] → 统一 `impactType` 允许后续新增来源，不破坏已有前端结构。
- [跨项目误读] → 服务层校验字段 `projectId`，所有下游查询都带项目或字段归属约束。
