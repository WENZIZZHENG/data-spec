# 设计

## 方案

第一版采用“源码级冒烟 + 现有构建门禁”的组合：

- 新增 `dataspec-web/tests/frontendSmoke.test.ts`，使用 Node 内置 `node:test` 读取路由、页面、store 和 API wrapper 源文件。
- 测试聚焦关键流程的可回归契约：
  - 路由必须保留 SQL 校验、反向导入、字段库、DDL 生成、AI Context、覆盖率、AI 回放等入口。
  - 顶部项目选择必须继续通过 project store 加载项目并绑定当前项目。
  - SQL 校验页必须保留 lint、fixedSql、检查记录和记录详情入口。
  - 反向导入页必须保留数据库直连、metadata 预览、compare、候选导入和本地状态记忆。
  - 字段库必须保留分页查询、关键词筛选、分组、批量维护和回退入口。
  - DDL 生成和 AI Context 页面必须继续调用对应 API，并处理项目 ID。
- 将测试文件加入 `dataspec-web/package.json` 的 `test` 脚本，使 `pnpm test` 一条命令覆盖这组冒烟约束。

## 取舍

- 不引入 Playwright。当前待办明确“不引入重量级测试平台”，仓库也已有 `node --test` 模式；第一版先保障关键源码契约和类型构建。
- 不做像素截图或真实浏览器点击。页面渲染细节留给后续更完整 E2E；本轮目标是防止路由、API、按钮和项目状态联动静默断裂。
- 测试使用少量源文本断言。它不替代组件单测，但能低成本覆盖页面和 wrapper 的关键耦合点。

## 风险与缓解

- 源文本测试可能因为重构命名产生误报：断言只覆盖用户可观察流程需要的稳定标识、API 函数和路由路径，避免检查样式或无关实现细节。
- 冒烟门禁不能证明真实后端数据可用：仍配合 `pnpm build` 和后端测试；README 明确其范围。
- 页面新增合法替代实现时需要更新测试：这正是门禁的目的，促使开发者同步说明关键流程变化。
