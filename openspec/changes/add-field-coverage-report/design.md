## Context

现有反向导入链路已经能从 SQL DDL 或数据库直连 metadata 得到 `TableDef/ColumnDef`，并能和标准字段库做字段名/别名比对。但这些能力目前主要服务“导入候选”和“差异比对”，缺少一个面向日常治理和 AI 使用的覆盖率总览：当前库里哪些字段已被标准覆盖，哪些未纳管，哪些缺注释或疑似重复。

P6-2 的目标是把现有解析、metadata 和字段匹配能力组合成即时覆盖率报告。它应帮助用户决定下一步补哪些标准，而不是引入后台同步、扫描业务数据或复杂治理流程。

## Goals / Non-Goals

**Goals:**

- 基于数据库直连 metadata 或 SQL/DDL 输入生成字段覆盖率报告。
- 输出项目级 summary、表级 summary、字段级明细和未纳管字段排行。
- 字段状态至少区分 `STANDARD_MATCH`、`ALIAS_MATCH`、`UNMANAGED`、`MISSING_COMMENT`、`POSSIBLE_DUPLICATE`。
- 复用字段名、别名和轻量语义推荐逻辑，避免与反向导入/字段推荐口径明显不一致。
- 前端提供可用入口，支持连接数据库、选择表、生成报告、按表/状态筛选和跳转补标准。

**Non-Goals:**

- 不扫描业务数据行，不做敏感数据采样。
- 不保存数据库密码、完整连接串或覆盖率历史趋势。
- 不自动导入未纳管字段，不自动合并重复字段。
- 不实现定时同步、后台任务队列或组织级治理看板。

## Decisions

1. 第一版使用即时报告，不新增持久化表。
   - 原因：覆盖率报告直接从当前标准和当前库结构生成，个人/小团队更关心当下行动；历史趋势可后续在 P6 性能/反馈任务中单独设计。
   - 替代方案：保存每次报告。暂不采用，避免模型过早膨胀。

2. 新增独立 `coverage` 后端模块，但复用 `reverseimport` 的输入能力。
   - 原因：覆盖率是新的用户语义，独立模块让 API、模型和前端命名更清晰；数据库直连读取仍由 `DatabaseReverseImportService` 的 metadata 能力派生或复用。
   - 替代方案：把所有代码塞进 `ReverseImportService`。暂不采用，避免反向导入承担过多报告职责。

3. 字段匹配先按标准字段名和别名确定命中，再用字段推荐/语义组识别疑似重复。
   - 原因：覆盖率百分比必须稳定、可解释；语义相似只能作为提示，不能把未命中字段算成标准覆盖。
   - 取舍：第一版可能漏掉一些复杂业务同义词，但避免误把新字段标成已覆盖。

4. 数据库直连报告复用现有连接请求模型。
   - 原因：前端已有非敏感连接记忆、表选择和直连流程；复用可减少用户重复输入。
   - 约束：请求仍包含当次 password，但不持久化、不写日志、不出现在报告结果中。

## Risks / Trade-offs

- [语义重复误判] → 只标记为 `POSSIBLE_DUPLICATE`，不计入覆盖率，原因里展示候选标准字段。
- [大库报告较慢] → 第一版要求用户选择表；后续 P6-16 再做大库性能基线和限流提示。
- [字段推荐口径分散] → 抽出轻量匹配 helper 或复用 `FieldService.suggest` 的公开结果，测试锁住典型样例。
- [数据库连接失败泄漏敏感信息] → 复用现有错误处理，不返回 password/JDBC URL；后续 P6-25 再补只读安全诊断。

## Migration Plan

1. 新增报告模型、服务、Controller 和单元测试。
2. 新增数据库直连 report API，基于现有 metadata 读取生成 `TableDef` 后调用报告服务。
3. 新增前端页面/入口和 API 封装，复用反向导入连接表单的关键字段。
4. 更新 README/TODO 和 OpenSpec 任务状态。
5. 验证通过后提交；不需要数据库迁移，回滚只需删除新增代码和入口。
