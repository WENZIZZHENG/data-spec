## Context

当前 `FieldServiceImpl.suggest` 会把用户输入压缩成 compact 字符串和 token 集，然后分别匹配字段名、显示名、注释、分类、标签和别名。这个实现简单可靠，但对 AI 常见输入还偏弱：中文描述可能只写“用户手机”“付款金额”，也可能用 `uid`、`sjh`、`mobile`、`tel` 这类英文或拼音缩写；同时“用户”“订单”“金额”这类泛化词如果权重过高，会把不够精确的字段推到前面。

P5-6 的目标是在不引入外部 LLM、不改变 API 结构的前提下，提升确定性推荐质量，让 AI 在建表前更稳定地复用个人标准字段。

## Goals / Non-Goals

**Goals:**

- 支持轻量内置语义词库，覆盖常见中文同义词、英文别名和拼音缩写。
- 对语义组命中输出可解释原因，例如“语义词命中: mobile”。
- 对泛化词降权，减少只因“用户”“订单”“金额”等宽泛词造成的误排序。
- 敏感字段被推荐时，在 `matchReason` 中追加敏感提示。
- fallback 候选名优先生成更标准的 `user_id`、`mobile_no`、`amount_cent` 等名称。

**Non-Goals:**

- 不调用外部 LLM，不引入向量数据库或全文检索服务。
- 不新增数据库表、迁移或 API 字段。
- 不替代后续 P6 的字段冲突检测、质量评分或按需 AI Context。

## Decisions

1. **在服务内使用静态语义词库**
   - 词库按 canonical token 分组，例如 `mobile`、`user_id`、`amount_cent`。
   - 每组维护中文、英文、拼音缩写和常见字段别名。
   - 理由：个人/小团队场景优先稳定和可测试；静态词库比外部模型更可复现。
   - 替代方案：把词库放入数据库配置。第一版不做，因为会扩大配置、导入导出和前端维护范围。

2. **评分仍是确定性加权，不改返回结构**
   - 现有 exact/contains/token 匹配保留，语义组命中作为新的候选分数来源。
   - 多个命中取最高分，并在排序时继续按分数和推荐名稳定排序。
   - 理由：CLI/MCP 和前端已经消费 `FieldSuggestion`，兼容性比模型“更漂亮”更重要。

3. **泛化词使用惩罚而非直接过滤**
   - 只命中 `user/order/amount/status/time/date` 等泛化词时降低分数；如果同时命中 `mobile/id/cent` 等精确词，则保留精确命中的高分。
   - 理由：泛化词有信息价值，但不能盖过更具体的标准字段。

4. **敏感提示写入 `matchReason`**
   - 命中敏感字段时追加“敏感字段”提示，不改变 score 和字段结构。
   - 理由：AI 和前端都已经展示 match reason，兼容地暴露安全语义即可。

## Risks / Trade-offs

- **静态词库不完整** → 第一版只覆盖当前 TODO 明确提到和项目标准中最常见的词，后续可随 fixtures 扩展。
- **语义词误命中** → 使用精确组交集和泛化词降权，避免只靠单个宽泛词排序靠前。
- **matchReason 文案变化影响断言** → 测试只断言关键片段，不依赖完整长句。
- **fallback 命名偏业务约定** → 只处理高频确定词；未知描述仍回落到现有 snake_case 生成。
