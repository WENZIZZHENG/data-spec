## 队列规则

- 活跃队列按主题推进，不再按原编号线性顺扫。
- 每个主题第一版只完成“近期范围”，其余原编号作为可选子项，不自动扩张范围。
- 只有出现本文件写明的触发条件，暂缓主题才进入 OpenSpec 或开发计划。
- 当前共 10 个实施主题，承接 36 个原候选编号。

## 近期队列

### 1. P6-137：`.dataspec/config.json` Schema 与编辑器提示

- 原编号：`P6-137`、`P6-173`。
- 为什么值得做：配置文件已是 CLI、MCP 和业务仓库集成的稳定入口，但目前缺少可校验的 JSON Schema；这是低成本、跨入口受益的确定性改进。
- 近期范围：提供 JSON Schema、字段说明、版本字段和最小编辑器关联示例；不开发 VS Code 插件。
- 验收：错误配置能被本地校验发现，AI 和编辑器能读取字段说明，CLI 测试覆盖兼容配置。
- 估算：0.5-1 个工作日。

### 2. P6-85：本地数据清理、重置与演示项目重建

- 原编号：`P6-85`。
- 为什么值得做：个人本地反复演示和验证会留下测试记录，当前缺少明确、可预览的项目级清理入口。
- 近期范围：演示项目重建和项目级 dry-run 清理；保留正式标准、Token、连接预设和备份恢复边界。
- 验收：用户能预览将删除的数据，显式确认后重建演示项目，不影响其他项目和安全配置。
- 估算：1-2 个工作日。

### 3. P6-86：前端性能体验与字段库密集操作

- 原编号：`P6-86`、`P6-122`、`P6-145`、`P6-151`。
- 为什么值得做：后端已有大字段库性能基线，但前端缺少请求/渲染耗时、慢页面状态和密集表格操作的用户可见反馈。
- 近期范围：先测量字段库和两个高频慢页面，增加慢状态提示、分页或必要的渲染优化；延续 P6-84 的键盘基线。
- 验收：慢请求和慢渲染可定位，字段库在目标数据量下滚动、筛选和键盘操作无明显卡顿，关键路径有浏览器测试。
- 边界：问题反馈导出和通用错误 Action 只在本主题产生真实证据时补，不建设遥测平台。
- 估算：2-4 个工作日。

### 4. P6-101：环境运行指纹与漂移诊断

- 原编号：`P6-101`、`P6-103`、`P6-118`、`P6-119`。
- 为什么值得做：可复现的运行指纹能让 AI 快速识别服务版本、配置和标准快照是否过期，可复用现有 doctor 与版本握手能力。
- 近期范围：输出本地配置、服务版本、API schema hash、当前标准快照和关键能力摘要；只在诊断关联确有需要时增加 correlationId。
- 验收：同一环境输出稳定指纹，配置或服务版本变化会产生可解释差异，结果默认脱敏。
- 边界：不接远程观测平台，不做全链路 tracing。
- 估算：2-3 个工作日。

### 5. P6-111：标准候选来源管道

- 原编号：`P6-110`、`P6-111`、`P6-112`、`P6-113`、`P6-124`、`P6-136`、`P6-142`。
- 为什么值得做：候选 Inbox 和维护 workflow 已存在，下一步价值在于把现有安全信号稳定送入 Inbox，而不是再造一个工作台。
- 近期范围：先接入 DataSpec 已有的覆盖率、反向导入、字段推荐未命中和 AI 反馈来源，统一来源证据与去重键。
- 验收：同一事实不会重复入箱，候选可追溯来源并进入现有决策流程，写入前有 dry-run 和人工确认。
- 边界：文档/ORM 解析、多数据源冲突和批量 apply 仅在对应来源出现真实需求后分阶段加入。
- 估算：3-5 个工作日。

### 6. P6-120：AI 场景回放与规则回归基线

- 原编号：`P6-120`、`P6-126`、`P6-133`、`P6-162`。
- 为什么值得做：现有 synthetic examples、golden fixtures 和 CLI/MCP 契约测试覆盖单点契约，但还缺少少量完整 AI 使用链路的确定性回放。
- 近期范围：先固化 3-4 条高频场景，覆盖启动握手、最小 Context、SQL 检查和标准维护；复用现有 fixture，不调用外部 LLM。
- 验收：关键场景可一条命令回放，规则或标准变更导致结果退化时能定位到具体样例。
- 边界：变异测试、A/B 评测和覆盖率报告只在基础回放稳定后增量加入。
- 估算：3-5 个工作日。

## 暂缓主题

### 7. P6-74：标准变更 diff、发布说明与迁移预演

- 原编号：`P6-74`、`P6-80`、`P6-98`、`P6-108`、`P6-117`、`P6-139`、`P6-160`。
- 保留原因：现有 What-if、Schema Plan 和代码 Patch Plan 已覆盖基础预览；仍可能需要跨标准包的统一 diff 和 AI 可读发布说明。
- 启动条件：出现真实标准包升级，且现有预览无法说明兼容影响或迁移步骤。
- 第一版边界：只做结构化 diff、release note 和验证命令，不建设自动迁移引擎。
- 估算：3-5 个工作日。

### 8. P6-104：标准决策理由与字段 ADR

- 原编号：`P6-104`。
- 保留原因：AI 需要理解“为什么采用这个命名或规则”，但当前来源、变更日志和证据已能满足多数场景。
- 启动条件：重复命名争议或规则取舍开始造成明显返工。
- 第一版边界：复用现有变更记录增加简短 decision note，不建设独立 ADR 平台。
- 估算：1-2 个工作日。

### 9. P6-123：标准消费 Schema 与轻量 SDK 导出

- 原编号：`P6-123`、`P6-154`、`P6-174`。
- 保留原因：标准最终可能需要被 API、DTO 或类型常量直接消费，但当前没有明确消费仓库和协议范围。
- 启动条件：至少一个真实业务仓库明确需要 JSON Schema、OpenAPI fragment 或语言常量包。
- 第一版边界：只支持一个已确认目标，不同时铺开 Protobuf、Avro 和多语言 SDK。
- 估算：3-5 个工作日。

### 10. P6-129：标准包 Lockfile 与同步漂移

- 原编号：`P6-127`、`P6-129`、`P6-149`。
- 保留原因：多业务仓库消费同一标准包时需要锁定版本并判断本地缓存漂移，但当前消费端规模尚小。
- 启动条件：两个以上业务仓库开始共享标准包，或发生过因版本不一致导致的错误。
- 第一版边界：只记录 pack version、snapshot hash 和 Context hash，不建设远程包仓库。
- 估算：2-4 个工作日。
